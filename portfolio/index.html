Enquiries stalled between the contact form and the diary.

Someone reads about a project and wants twenty minutes to find out whether their own job is feasible. They meet a contact form that disappears into an inbox. Two days later a partner replies offering three times, and one is already gone. The thread runs four messages before anything reaches a diary, and some prospects give up in the middle.

The practice also cannot show its work properly. Every project has facts a prospective client wants first: where, how big, how long, which disciplines. Those facts were retyped into prose, so they disagreed between pages and could not be filtered.

What finished looks like, stated so it can be checked:

  • A visitor picks a slot and receives a confirmation in one visit, with no email exchange.
  • Two people clicking the same slot at the same moment produce exactly one booking.
  • Each project's facts are entered once and render identically everywhere they appear.
  • The site is fast and structured enough that the work can be found.

Eastern Standard Studio is invented. The practice, its projects and its address are fictional, and this build was self-initiated.

One slot holds one booking, and the database enforces it.

Correctness

Make double booking a database problem

The obvious build reads "is this slot free?" and then writes. Two simultaneous requests both pass the read. That window is milliseconds wide, and a double-booked principal is the exact failure a booking system exists to prevent, so the guarantee sits in a UNIQUE KEY.

wp_ess_slot_locksUNIQUE KEY slot_start409 on conflict

Scope

Build the booking engine in code

A booking plugin carries settings for every case this practice does not have: one appointment type, one calendar, a fixed weekly pattern. The only hard question in it is the one a plugin would hide.

Structure

Keep the data out of the theme

Everything functional sits in a plugin and the theme only renders. A redesign in three years should not take the appointments with it.

Automation

Host the automation on the same network

A cloud automation platform cannot reach a local site without a tunnel whose URL changes on every restart. n8n on the same Docker network has a hostname that never moves, and the workflow ships as a JSON file in the repository that setup.sh imports.

What one booking does.

The steps run on every booking request. The table beside them lists one decision per layer and what it buys.

  1. Guard the requestNonce, honeypot, a signed render stamp and a per-address rate limit, all checked before anything is written.
  2. Resolve the slot on the serverA submitted timestamp is never trusted. It is matched against the slots the studio publishes, or a crafted request could book 3 am on a Sunday.
  3. Create the record, then claim the lockIf the claim loses the race, the record is deleted again, so a rejected booking leaves nothing behind.
  4. Hand off to the automationThe payload carries its own callback URL, so the workflow never hardcodes where the site lives.
  5. Confirm backn8n sends both emails and calls a signed REST route that marks the booking confirmed and timestamps it.
  6. Recover when it does notA booking with no callback stays pending, and an hourly job releases the hold after 30 minutes. A broken workflow costs one slot for half an hour.

ess-core/includes/class-availability.php

// PHP silently rolls a non-existent local time forward on a spring-forward
// day. Comparing the result back catches a slot no clock ever shows.
$built = DateTimeImmutable::createFromFormat( 'Y-m-d H:i', "$date $time", $tz );

if ( ! $built || $built->format( 'Y-m-d H:i' ) !== "$date $time" ) {
    return null;
}
